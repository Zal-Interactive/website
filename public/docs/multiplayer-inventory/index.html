Multiplayer Inventory

com.zalinteractive.multiplayer-inventory

Overview

Multiplayer Inventory is a server-authoritative grid and slot inventory for Netcode for GameObjects (NGO). It ships the inventory logic, the network sync, JSON persistence and uGUI views.

Features

  • Grid containers and single-slot containers (equipment slots), on players, chests and dropped items.
  • Stacking, splitting, rotating, quick-move and drag and drop.
  • Nested containers: an item such as a pouch owns containers of its own.
  • Custom per-item data (metadata) that is replicated to clients.
  • Server-authoritative operations. Clients send requests, the server decides and replicates the result.
  • Pickups, loot tables and a loot spawner.
  • Save and load of items through JSON files, with an auto-saver.
  • Extension points for validation, item use, context menus, item views, details panels, input and localization.

Run the sample

The fastest way to see the inventory work is the Basic Inventory sample. It is a playable host scene with a player, equipment slots, pickups, a lootable chest, persistence and every UI prefab you need.

  1. Open Window > Package Manager and select Multiplayer Inventory.
  2. Open the Samples tab and click Import next to Basic Inventory. The sample lands in Assets/Samples/Multiplayer Inventory/<version>/Basic Inventory.
  3. Open Scenes/BasicInventory.unity from the imported folder.
  4. Add the scene to File > Build Settings > Scenes In Build. NGO asks for this when it starts a session. Without it, NGO shows a prompt about the scene.
  5. Press Play. The scene starts a host on its own.

Set up your own scene

Use the sample scene and prefabs as a reference. The minimum for a working inventory is:

  1. Create an Item Database (Assets > Create > Multiplayer Inventory > Item Database) and an Inventory Configurations asset that references it.
  2. Create item definitions (Assets > Create > Multiplayer Inventory > Item Definition) and add them to the database. In Inventory Configurations, assign Item View Prefab, Item Context Prefab, Dynamic Inventory View Prefab, Item Preview Prefab and Pickup Prefab using the sample prefabs as a reference.
  3. Add Inventory Setup (and Inventory Input Setup for the Input System) to a scene object, and assign the configurations asset.
  4. Build a player prefab with a NetworkObject, Inventory Component, Inventory Syncer, Player Inventory Actions and Inventory UI Opener.
  5. Add a GameplayScope (Autofac Unity) to the scene. It finds the package installers on its own. Add one installer of your own that calls AddZalUI. See Register the installers.
  6. Register network prefabs with NGO and window view prefabs with Zal UI. See Connect Zal UI.

The sample’s player prefab has these components: InventoryComponent, InventorySyncer, PlayerInventoryActions, InventoryUIOpener and ServerInventoryAutoSaver, plus the sample scripts for movement, interaction and the starter loadout. The sample chest has InventoryComponent, InventorySyncer, LootSpawner and LootingInventoryInteractionReceiver.

Item definitions and the database

An Item Definition (ItemDefinition) describes one kind of item: icon, world model, size, weight, stacking and the containers it owns. Subclass it to add your own data. Subclasses need their own CreateAssetMenu.

Field Meaning
Icon, WorldVisualPrefab, GameplayPrefab What the item looks like in the UI, in the world and when equipped
CustomInventoryViewPrefab A view prefab for the item’s own containers. Empty uses the default view
GenerateLivePreview Render a live 3D preview instead of the icon
CanRotate, Size Rotation and the size in grid cells
IsStackable, MaxStack Several instances merge into one stack, up to MaxStack
Weight Weight of one unit. It is reported but not enforced. See Known Gaps
Containers The containers the item owns, such as the pockets of a backpack
AssignableSlots The SlotType assets the item fits
MatchingFilters The ContainerTag assets that let filtered containers accept the item
DefaultSubItems Items created inside the item when it is created

A stackable item cannot own containers or default sub-items. The definition logs an error and clears IsStackable if you set both.

The Item Database (ItemDatabase) is the default ordered list of definitions. The one-based index of a definition is its ItemId. Keep the order stable during a session and identical on the server and every client. A project can replace the database list with an IItemDefinitionSource; see Provide your own item definitions.

The inspector of the database has an Add Missing Item Definitions button. It finds every ItemDefinition in the project that is not listed yet and appends it at the end. Inventory Configurations references the fallback database and holds the shared prefabs: item view, context menu, dynamic inventory view, item preview and networked pickup. It also holds the grid cell size, cell prefab, drag conflict behaviour and item search duration. A custom source does not need an assigned database; it still needs the configurations asset for these settings.

Saves store the definition’s asset name (ItemIdAuthoring), not the numeric id. Keep asset names stable once players have saves.

Containers, grids and slots

An inventory owner has a list of containers (ContainerDefinition). The owner is a network object with an InventoryComponent, or an item that owns containers.

  • A grid container (IsGrid) has a width and a height in cells. Items occupy Size cells and can be rotated when CanRotate is set.
  • A slot container is a single place. Its SlotType asset decides which items fit: the item must list that slot type in AssignableSlots.

SlotType assets (Assets > Create > Multiplayer Inventory > Slot Type) are labels such as Head or Hand. InventoryComponent.GetAssignedItem(slotType) returns the item in the container with that slot type.

Filters. A container with ExtraFilters accepts only items whose MatchingFilters share a ContainerTag (Create > Multiplayer Inventory > Container Tag). An empty filter list accepts everything. See Known Gaps: the filter does not stop a merge into an existing stack.

Stacking. Stackable items merge up to MaxStack. Inventory.Merge fills a target stack. Inventory.SplitItemIntoWithRemainder takes part of a stack and returns what did not fit.

Nested containers. An item whose definition has Containers is itself an inventory owner. Its items are saved with it and replicate with the root owner. The UI opens such an item from the context menu (Open) into a popup.

Facade. The static Inventory class is the entry point for code, for example Inventory.SpawnItemsInto(inventoryId, itemId, count), Inventory.MoveItemInto, Inventory.GetItemCount, Inventory.CheckItems and Inventory.ConsumeItems. Call these on the server. The facade is available once the MultiplayerInventoryInstaller has run in the gameplay scope.

Item metadata

Metadata is custom data on one item instance, such as durability. Implement IItemMetadata with a public parameterless constructor. Write and read your fields in the same order. Register the type on the server and on every client.

public class DurabilityMetadata : IItemMetadata
{
    public int Durability;

    public void Serialize(BinaryWriter writer) => writer.Write(Durability);

    public void Deserialize(BinaryReader reader) => Durability = reader.ReadInt32();
}

Inventory.RegisterMetadataType<DurabilityMetadata>();
Inventory.SetMetadata(item.InstanceId, new DurabilityMetadata { Durability = 100 });
var durability = Inventory.GetMetadata<DurabilityMetadata>(item.InstanceId);

SetMetadata replicates from the server. Metadata is not written to save files in this version. DeleteItemMetadata removes an entry. Metadata is part of the full sync a late joiner receives. Register metadata types before the first item is replicated. The type id is a hash of the type’s full name, so server and clients must be builds that compute the same hash.

Networking model

The server owns the truth. Every inventory change happens on the server, which then tells the clients.

  1. A client acts in the UI. PlayerInventoryActions checks the player’s authority locally, sends a server RPC (MoveItemServerRpc, SplitItemServerRpc, PickupServerRpc, DiscardServerRpc, MoveItemsIntoServerRpc, SplitItemIntoServerRpc) and also applies the change locally.
  2. The server runs the same action against its repository: merge, place, split or move.
  3. InventorySyncer on the server sends the resulting item (UpdateItemClientRpc), a deletion (DeleteItemClientRpc) or a metadata change to the clients.

Full-item sync. An update carries the whole InventoryItem: instance id, item id, count, placement and container. Clients overwrite their copy. There are no deltas.

Late join. When an InventorySyncer spawns on a client, it asks the server for everything with RequestItemsFromServerRpc. The server answers that client only, with all items of the owner (including nested items) and their metadata. When the object despawns on a client, the client unloads its copy of those items.

Observers. Update RPCs use SendTo.NotServer, so every client that has the object spawned receives every update of that inventory, including other players’ inventories. See Known Gaps.

Host mode. A host shares one repository between its server and its client. There is no separate replica on the host.

Authority

IAuthorityChecker decides whether a sender may operate on an item, a container or an inventory. The Netcode implementation grants access when:

  • the inventory is the player’s own (the owner id equals the player’s network object id),
  • the inventory belongs to a network object whose InventoryComponent has Is World Inventory set (chests, pickups, dropped loot), or
  • the inventory belongs to an item, and the root owner of that item passes one of the rules above.

Move and split requests check the authority over the source item and over the target container. Pickup, discard and MoveItemsInto do not check authority. See Known Gaps.

World inventories are open to every player at the same time. The package does not lock a chest to one player and does not check distance. Your interaction code decides who may open one.

Loot. LootSpawner fills its inventory on the server from a LootTable (weighted entries, a spawn chance and a count range). PickupFactory.Create(item, position) spawns a pickup from the pickup prefab in Inventory Configurations and moves an item into it. The server does this when a player discards an item.

Persistence

Persistence saves the items of an owner as a JSON file and recreates them when you load.

Scene objects. Add PersistentInventoryId to a scene object. The editor generates a GUID when the component is added. Do not copy the same id to two objects. A prefab asset gets no id, so instances need their own id in the scene.

Players. Player objects are identified by the IPlayerPersistenceIdProvider you register, not by PersistentInventoryId. The default provider returns "player-" + clientId. Netcode assigns client ids per connection, so this id only lasts for one session. Ship your own provider that returns an id from your account or authentication system. The id must be unique per player and safe to use as a file name.

public class AccountPlayerIdProvider : IPlayerPersistenceIdProvider
{
    public string GetPersistenceId(ulong clientId) => Accounts.GetAccountId(clientId);
}

Saving. Add ServerInventoryAutoSaver to the network object. It saves on the server after the last change, once DebounceDelayMs (default 250) has passed without another change. You can also call InventoryPersistenceManager.SaveEntityItems(inventoryId) yourself.

Loading. Loading is not automatic. Call InventoryPersistenceManager.LoadEntityItems(persistenceId) on the server after the owner has spawned. The sample’s SamplePlayerLoadout loads the player’s save and grants starter items if nothing was saved.

Storage. The default storage writes one file per owner to Application.persistentDataPath/InventoryPersistence/<id>.json. Characters that are invalid in file names become _. A file holds the item asset names, counts, placements and container indexes, with nested items inside their parent. Register your own IPersistentDataStorage to save elsewhere, such as a database or a cloud service.

WebGL. WebGL has no threads, so the save runs on the calling thread instead of a background task. A save blocks the frame while it writes. Use a longer debounce delay on WebGL.

Not saved. Metadata is not part of the JSON file in this version. The saved format keeps the item, count, placement and nested items.

Provide your own item definitions

Implement IItemDefinitionSource in your runtime assembly and register it in an IGameplayInstaller. The package uses your source instead of Item Database, regardless of installer order. Return the complete list synchronously; finish any loading before the first inventory lookup.

This example loads definitions from Resources/InventoryItems and sorts by asset name:

using System;
using System.Collections.Generic;
using System.Linq;
using Autofac;
using UnityEngine;
using Zal.AutofacUnity;
using Zal.MultiplayerInventory;

public class GameItemDefinitionSource : IItemDefinitionSource
{
    public IReadOnlyList<ItemDefinition> Items { get; }

    public GameItemDefinitionSource()
    {
        Items = Resources.LoadAll<ItemDefinition>("InventoryItems")
            .OrderBy(item => item.Id.Value, StringComparer.Ordinal)
            .ToArray();
    }
}

public class GameInventoryInstaller : IGameplayInstaller
{
    public void Configure(ContainerBuilder builder)
    {
        builder.RegisterType<GameItemDefinitionSource>()
            .As<IItemDefinitionSource>().SingleInstance();
    }
}

Replace the loading code with your project’s catalogue or preloaded definitions. Return a non-null list with no null entries. An empty custom list remains empty; it does not enable the database fallback.

The numeric ItemId is the one-based list position. Keep the list stable during a session and identical on every multiplayer peer. The example’s name sorting gives the same order when all peers have the same assets. Saves use asset names, so keep names stable too.

Show custom definitions in the Editor

Add a class implementing IItemDefinitionSourceInstaller to your project’s Editor assembly. Give it a public parameterless constructor. The Editor discovers it automatically and uses its source for item-ID dropdowns outside Play Mode.

using Autofac;
using Zal.MultiplayerInventory;
using Zal.MultiplayerInventory.Editor;

public class GameItemDefinitionEditorInstaller
    : IItemDefinitionSourceInstaller
{
    public void Configure(ContainerBuilder builder)
    {
        builder.RegisterType<GameItemDefinitionSource>()
            .As<IItemDefinitionSource>().SingleInstance();
    }
}

If you use assembly definitions, reference Zal.MultiplayerInventory, Zal.MultiplayerInventory.Editor, your runtime source assembly and Autofac.dll. Register any dependencies the source requires here as well. The Editor container is separate from gameplay; registration must not start gameplay services.

Register one custom source in each container and expose the same definitions. Without an Editor installer, dropdowns collect names from all project Item Database assets. Without a runtime registration, runtime lookup uses the database assigned to Inventory Configurations.

Select a component containing an item-ID field and open its dropdown. Your custom definitions appear; a stored value absent from the list remains visible with (missing). Project changes refresh the list and recreate the Editor container. Play Mode transitions and assembly reload also dispose it. A failing installer or source reports an error; it does not silently substitute database definitions.

Moving from database prefab settings

Shared prefab properties now belong to InventoryConfigurations; the old ItemDatabase prefab properties have been removed. Update code such as config.ItemDatabase.PickupPrefab to config.PickupPrefab.

Before upgrading an existing project, record the five prefab assignments from each database. After upgrading, assign those references to every Inventory Configurations asset that used it. The repository’s Basic Inventory sample and packaged sample have already been migrated. Definition order and asset GUIDs are unchanged.

Extension examples

A validator and a use handler:

public class NoRingsInBackpack : ICustomOperationValidator
{
    public ValidationResult CanItemBeAdded(ContainerId containerId, ItemId id, int count)
        => id.Definition.name == "Ring" ? ValidationResult.Denied : ValidationResult.Unhandled;

    public ValidationResult CanItemBeRemoved(ContainerId containerId, ItemId id, int count)
        => ValidationResult.Unhandled;
}

public class PotionUseHandler : IItemUseHandler
{
    public bool TryUseItem(in InventoryItem item)
    {
        if (item.GetDefinition() is not PotionDefinition potion)
            return false;
        potion.Drink();
        return true;
    }
}

Platform notes

The package targets PC, mobile, console and WebGL. The runtime code has no platform-specific API except the points below.

WebGL. Browsers cannot open raw sockets. Set the NGO UnityTransport to WebSocket mode, on the server and the client. Saves run synchronously on the main thread because WebGL has no background threads. See Persistence.

Mobile. The Input System bindings include touch for placing items and for the pointer position. The default bindings do not cover split, discard, rotate or quick transfer on touch. Add touch bindings for those actions to your own actions asset.

Console and gamepad. The default actions bind the gamepad to every inventory action. The inventory is pointer-driven, however: it reads the Point action for the cursor position, and the default asset binds no gamepad control to it. On a gamepad, drive a virtual cursor (for example the Input System VirtualMouse) that writes the Pointer position. Without one, the gamepad can press buttons but nothing is under the pointer.

Saves. Application.persistentDataPath must be writable. On a platform where it is not, register your own IPersistentDataStorage.

Known Gaps

This version ports an existing inventory as it was. These gaps exist in 0.1.0. Four are covered by tests that fail while the gap exists (category KnownGaps). Plan for each one before you ship a competitive or trading game.

Tested gaps

# Gap What to do today
1 A server move into a container whose filter rejects the item still succeeds when the item merges into an existing stack. The merge lookup does not consult the container filter. Do not put stackable items into a filtered container. Make items that a filter must reject non-stackable, or keep stacks of that item out of that container. Check the target container in your own server code before you move an item for the player.
2 ICustomOperationValidator is not consulted when stacks merge. Do not rely on a validator for merges. Enforce the rule in your server code before the operation, or make the item non-stackable.
3 ICustomOperationValidator is not consulted when an item is placed. Check the rule in your own server code before calling Inventory.PlaceItem. Assume a player request can place an item.
4 ICustomOperationValidator is not consulted when an item is moved into an inventory (MoveItemInto). Check the rule in your server code before you call MoveItemInto. Treat validators as honoured by split only.

Untested gaps

Gap What to do today
Weight is not enforced. ItemDefinition.Weight is reported but nothing has a weight limit. Sum Weight times Count over Inventory.GetInventoryItemsRecursive in your server code and refuse to grant items over your limit. Slow the player down with the same sum.
Pickup has no range check. The server accepts a pickup request for any pickup, at any distance. Treat Pickup.RequestPickup() as the only normal route and run it from interaction code that checks range. Use NGO object visibility (NetworkObject.NetworkHide) so far pickups are not sent to a client. A modified client that guesses an id can still send the request, so this reduces the risk and does not remove it.
Updates are broadcast to all observing clients. Every client that has an inventory’s network object spawned receives every update of it, including other players’ private inventories. Never store secrets in items or metadata. Hide objects from clients that must not see them with NetworkHide. If another player’s inventory contents must stay private, this version is not suitable without changes.
The sync of a client replica cannot be tested in a single host process. A host shares one repository between server and client. Test replication with a real dedicated server and at least two clients.
Discard and MoveItemsInto do not check authority. A client can send these requests for item ids it does not own. Run extra checks in your own server code, and treat clients as trusted until this is fixed.
Metadata is not saved. Metadata replicates but is not written to save files. Store data that must survive a restart in your own save, or in the item count.
The default player persistence id is session-only. The default provider uses the Netcode client id. Register your own IPlayerPersistenceIdProvider. See Persistence.

Before you ship. Test with a real server and two clients. Review the server rules above against your game. A client cannot be trusted to enforce a rule that the server does not.
